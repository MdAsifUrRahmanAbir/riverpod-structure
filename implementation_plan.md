# Implementation Plan - Fix Riverpod Clean Architecture Generator & Feature Issues

This plan analyzes the POS Riverpod clean architecture structure generated by `generate_pos_riverpod.py`, identifies root causes of feature build failures, and outlines the fixes to both the Python automation script and the generated Flutter codebase.

## Root Causes of Issues

> [!IMPORTANT]
> **1. Incorrect Relative Import Paths**: The python templates used fixed `../../../` relative paths. Because screens in `lib/features/<name>/presentation/screens/` are 4 levels deep from `lib`, `../../../` resolved to `lib/features/core/` instead of `lib/core/`.
> 
> **2. Riverpod 3.x Syntax Incompatibility**: `pubspec.yaml` uses `flutter_riverpod: ^3.4.2`. The script generated legacy Riverpod `StateNotifier` / `StateNotifierProvider` classes, which are removed/deprecated in Riverpod 3.x, causing `extends_non_class` compilation errors.
> 
> **3. Screen vs Widget Naming Mismatches**: In `products`, the screen is `product_list_screen.dart`, while widgets were named `product_mobile_view.dart` and `product_tab_view.dart`. The generator template looked for `product_list_mobile_view.dart`, resulting in missing import errors.
> 
> **4. Unimplemented Core Placeholders & Main Entry Point**: Core files (`app_colors.dart`, `app_theme.dart`, models, etc.) were left with blank `// TODO` comments. `main.dart` retained the default Flutter counter app without `ProviderScope` or `GoRouter` setup.
